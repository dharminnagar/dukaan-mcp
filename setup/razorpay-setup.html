Razorpay Test Mode Setup

A one-time checklist to get a solo-dev, TEST-MODE-ONLY Razorpay integration working for a hackathon build (Bun/TypeScript, MCP server, AI buyer agents, policy gate). No KYC, no live money.

1

Account signup

Creates your Razorpay account. This step alone unlocks Test Mode — nothing else in this section is required for the hackathon.

Test Mode needs signup only — no KYC. Razorpay's own Quickstart docs describe Test Mode as usable immediately after signup, without completing KYC verification (their phrasing: you can "start integration immediately without KYC completion" and use Test Mode while KYC is pending or entirely skipped). Test Mode has no time limit on its own.

The 4–5-business-day-ish review you may have heard about applies only to Live Mode activation (accepting real money) and to partner/commission payout features — Razorpay's docs quote varying ranges depending on business type (roughly 1–5+ working days), with some accounts eligible for a faster "Express Activation." None of that blocks you. Do not start it.

4

Smoke test: create an order

Confirms your keys work before you build anything on top. Amount is in the smallest currency subunit — paise for INR (so ₹500.00 is 50000). The API base URL is identical for Test and Live — only the key prefix (rzp_test_ vs rzp_live_) and secret differ.

curl
curl -u rzp_test_xxxxxxxxxxxxxxxx:xxxxxxxxxxxxxxxxxxxxxxxxxxxx \
  -X POST https://api.razorpay.com/v1/orders \
  -H "Content-Type: application/json" \
  -d '{
    "amount": 50000,
    "currency": "INR",
    "receipt": "receipt#1"
  }'
orders.ts (Bun)
const keyId = process.env.RAZORPAY_KEY_ID!;
const keySecret = process.env.RAZORPAY_KEY_SECRET!;

const res = await fetch("https://api.razorpay.com/v1/orders", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: "Basic " + btoa(`${keyId}:${keySecret}`),
  },
  body: JSON.stringify({
    amount: 50000,
    currency: "INR",
    receipt: "receipt#1",
  }),
});

const order = await res.json();
console.log(order.id, order.status); // order_..., created

Both are long shots. S2S JSON v2 is an on-demand feature normally requiring a support-approved activation and, for card data, a PCI-DSS compliance certificate — a solo hackathon account may simply not qualify. BharatQR activation is also support-gated and, per Razorpay's docs, even once enabled its scanning flow only works against Live Mode QR codes (test mode has its own separate "BharatQR test payment route" for triggering test payments toward a test-mode QR). Lead time for either request is unknown and could exceed your deadline. Nothing in the build should depend on either being approved — use the Orders API (Section 4) as your primary rail.

  • OTP rule: enter any OTP 4–10 digits long to make the payment succeed; anything under 4 digits makes it fail. This applies to the mock OTP screen shown during test-mode card payments.
  • UPI test VPAs: success@razorpay simulates an instant successful payment; failure@razorpay simulates an instant decline.

UPI Collect is being deprecated 28 Feb 2026 per an NPCI mandate — manual VPA/UPI-ID entry to initiate a payment or mandate is being phased out industry-wide (a narrow MCC exemption exists for IPO/secondary-market transactions, which won't apply here). Razorpay will auto-remove the UPI Collect option from Standard Checkout; for Custom/S2S checkout integrations, removal and switching to UPI Intent/QR is a manual step on your side. Since this lands before your 5 Sept 2026 deadline, don't build anything that depends on UPI Collect specifically — use UPI Intent/QR flows, or the test VPAs above via whichever flow is still active when you test.

Confusing but confirmed: in test mode, clicking "cancel" on a payment results in a successful payment, not a cancelled/failed one. Razorpay's own docs state this directly. If you need to test a genuinely failed/cancelled payment, use the mock bank page's explicit "Failure" button, an OTP under 4 digits, or failure@razorpay — don't rely on the cancel action to simulate failure.

8

Known limits and blockers

Read this before architecture decisions, not after.

Practical conclusion: build your buyer-agent → policy-gate → payment flow around the Orders API (Section 4) as the rail — it's a clean server-to-server JSON call with no browser dependency. But expect payment authorization itself (actually moving a test payment from "created" to "paid") to require either a browser session hitting the Standard Checkout mock bank page, or a human clicking through it — plan your demo flow (and any automated agent test harness) around a human/browser step at the authorization boundary, not full end-to-end headless automation.
