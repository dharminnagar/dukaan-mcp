# projectmem - dukaan-mcp

_Last updated: 2026-08-25_

## Project purpose
A multi-tenant MCP server for the Razorpay AI Buildathon 2026 (Track 01). Any Razorpay merchant uploads a catalogue and a spend policy, and third-party AI buyer agents then shop and check out against it through one stable set of tools. Every money action passes through a policy gate that returns allow, block or escalate with a reason code, writes an audit row on every branch, and reports its own rule coverage and false-positive cost. The gate is the product; the catalogue and the MCP server exist so the gate has something to decide about.

Status 2026-08-24: Day 1 and Day 2 complete. 58 tests pass. The gate itself is not written yet (DUK-14).

- [DONE] #0018 SPEND CAP TOCTOU RACE, found by orchestrator probe against the DUK-13 checkout flow. Three checkouts fired CONCURRENTLY by the same agent, each 40000 paise against a 100000 cap: all three returned allow and 120000 paise persisted, breaching the cap by 20000. Cause: decide() reads spentInWindowPaise and the checkout handler writes the orders row in two separate statements with no transaction, lock, or serialisation between them, so concurrent checkouts all observe the same pre-write total. Reproduced deterministically with Promise.all over three calls. WHY THIS IS SIGNIFICANT RATHER THAN A GENERIC CONCURRENCY NIT: it is adversarial class #1, budget-split evasion, in its most direct form — parallel instead of sequential. The eval suite replays transcripts sequentially, so it will report budget-split as CAUGHT while the parallel variant escapes undetected. A metrics table claiming the cap holds, published next to a gate that a client can beat by issuing three simultaneous tool calls, is exactly the kind of gap the escapes list exists to surface. MCP clients can and do parallelise tool calls, so this is inside the declared threat model, not outside it. NOT a flaw in DUK-13's implementation, which follows the specified flow correctly; it is a gap in the gate's contract. PROPOSED FIX, cheap and non-invasive: take a Postgres transaction-scoped advisory lock keyed on (merchant_id, agent_id) in the CHECKOUT HANDLER around decide() plus insertOrder. That leaves decide() a pure function with injected deps, so src/eval/ is unaffected and the offline reproducibility property survives. Alternative if not fixed: state it plainly in the README limitations list next to the unauthenticated-agent-identity item, because a judge probing the gate will find it. [src/mcp/http.ts] -> DUK-29 spend-cap parallel race FIXED in commit 480c367. withAdvisoryLock(key, fn) added to src/db/pool.ts (one new export; pool, query, queryOne, withTransaction and closePool verified untouched): opens a short transaction on its own pooled client, takes SELECT pg_advisory_xact_lock(hashtext($1)), runs fn, commits. Transaction-scoped rather than session-scoped deliberately — Postgres releases it however the transaction ends, so nothing must remember to unlock if the process dies mid-checkout. The checkout handler in src/mcp/http.ts wraps decide(), the Razorpay call and insertOrder in one lock keyed `${merchant_id}:${agent_id}`. THE RAZORPAY CALL STAYS INSIDE THE LOCK: the lock must already be held when decide() runs because the branch is unknown until it returns, so releasing between decide() and insertOrder to spare the network round trip would merely shrink the race window rather than close it. Cost is that one agent serialises behind its own payment latency; other agents and merchants never contend since keys are independent. Escalate does not need the lock for correctness (SPEND_CAP_SQL filters status IN ('created','authorized'), so escalated orders never count) but ends up inside it structurally.
