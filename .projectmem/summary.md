# projectmem - dukaan-mcp

_Last updated: 2026-08-24_

## Project purpose
Hackathon project for the Razorpay Buildathon (Track 01 — AI Growth & Agentic Commerce). Intended build: a multi-tenant MCP server that lets any Razorpay merchant self-serve onboard a normalized catalog + spend policy, so third-party AI buyer agents can discover, shop, and check out against that merchant through one stable tool surface — with a gating middleware (spend cap, category allowlist, approval threshold, price/stock integrity) and a live audit trail over real Razorpay test-mode APIs. Personal goal behind the project: win/stand out at the buildathon and land a Razorpay internship.

Status as of 2026-08-22: **pre-code**. Only the idea doc exists. Idea is being stress-tested before any implementation.

## Decisions
- Target: Razorpay Buildathon Track 01 (AI Growth & Agentic Commerce). Concept = multi-tenant MCP server making any Razorpay merchant agent-transactable self-serve, vs the expected field of single-hardcoded-merchant chatbot+checkout builds. Stated success bar: stand out enough to land a Razorpay internship.
- Event is a BUILDATHON for internship shortlisting, not a prize hackathon. Internship stipend 75K stated on the site. Deliverable includes a PITCH VIDEO. Therefore optimize for hiring-signal (problem identification + AI-builder skill, legible on video) over feature count.
- Narrative framing chosen: merchant-side growth — 'merchant becomes discoverable to third-party AI shoppers and receives orders it would never otherwise see' — over consumer-restock or B2B-procurement framings. Rationale: matches Track 01 'AI Growth', makes the merchant (Razorpay's real customer) the beneficiary, and reframes onboarding as a distribution channel rather than plumbing. Builder also wants to foreground problem-identification skill (gap thesis (a)).
- Gap claim will be rescoped to India/UPI/Razorpay rails and will name Shopify UCP and Stripe Agentic Commerce Suite explicitly, with dates, in the pitch video. Rationale: the global version of the claim is false and naming the competition is a hiring signal; hiding it reads as junior. Supporting fact to cite: OpenAI retired Instant Checkout in March 2026 after fewer than 15 Shopify merchants went live, so merchant onboarding was genuinely the failure mode.
- Payment rail: use POST /v1/orders as the primary rail, not Payment Links. Payment Links are capped at 30 per business in test mode (confirmed verbatim; raisable only via support; lifetime-vs-rolling UNVERIFIABLE), they are a human-facing artifact, and an autonomous buyer agent should not mint them. Orders API has no documented test-mode cap. Razorpay publishes no numeric API rate limits at all — only the existence of a rate limiter and guidance to handle HTTP 429 with randomised exponential backoff. Implement 429 backoff and stop architecting around a number that does not exist publicly.
- TRACK LOCKED: Track 01 (AI Growth & Agentic Commerce). Rejected Track 03 (same headless blocker as 01, plus no programmatic failure generation and no retry API) and Track 04 (safe and API-independent via its explicit 'synthetic data' allowance, ~25hr build, but the track defines its own output format so every submission looks alike — forgettable for a hiring panel).
- PITCH REFRAMED: the product is the GATE, not the catalog. 'Agent-readable catalog' is Razorpay's own listed example for Track 01 and therefore the crowded framing. The non-obvious problem underneath: before a merchant can be exposed to AI buyers, someone must decide whether that merchant is SAFE to expose — Razorpay hand-picked Zomato/Swiggy/Zepto/Vi/BigBasket precisely because it could vouch for them, and self-serve means vouching at scale (catalog accuracy, price integrity, stock truthfulness). This is Bumblebee's problem shape pointed at agentic commerce. The catalog and multi-tenant MCP server remain, as substrate rather than as the headline.
- CROSS-TRACK GRAFT: import Track 02's bar ('honest metrics including false-positive cost') into Track 01. Treat the gate as a classifier and measure precision/recall over a held-out set of benign and adversarial agent sessions. Key insight tying the halves together: a false positive in the gate is a legitimate purchase blocked, i.e. merchant revenue lost — so false-positive cost denominated in rupees of blocked legitimate GMV is simultaneously the Track 02 honesty metric and the Track 01 GROWTH metric. Cost is a scripted session generator, not a new subsystem. Expected to be unique among Track 01 submissions.
- Payment loop closes via human-authorized handoff (option i): agent shops, gate decides, a real Order is created through POST /v1/orders, and authorization is a bounded approval step framed as UPI-compliant-by-design with the NPCI citation. Rationale: an agent cannot autonomously authorize a UPI payment under current Indian regulation — that is precisely why UPI Reserve Pay and NPCI's UAP exist — so this is the only currently-legal shape, and stating it explicitly is a stronger signal than faking autonomy. Rejected Playwright-driving-hosted-checkout (6-10hrs to fake an autonomy regulation forbids). S2S JSON v2 and BharatQR support tickets raised in parallel as a free upgrade if granted.
- Repo standard: tests on the gating middleware specifically (the gate is the pitch, and untested gating logic contradicts 'every money action bounded and gated'), plus a real architecture README and honest commit history. Rejected full coverage (no hours) and minimal-tests-lean-on-video (what most entrants will do). Builder is additionally using projectmem and skills to raise code and documentation quality as a differentiator.
- Scope: KEEP both the onboarding UI and the audit view. Builder overrode the recommendation to cut the audit view. Consequence to watch: the evaluation suite is the actual differentiator and is currently scheduled last, so it is what a late scope cut would hit. Feasibility review dispatched to confirm whether all 11 build items fit in ~40 hours.
- Pitch video structure: lead with the PROBLEM (option b) so the panel sees explicitly why this problem was chosen, then the demo, then close on the metrics table with the adversarial escapes named. Builder also wants a 'why I am the right fit to build this' section at the start.
- Evaluation suite consumes DETERMINISTIC SCRIPTED TRANSCRIPTS (JSON arrays of tool calls with asserted prices and quantities), not live Claude sessions. Saves ~3hrs plus API spend, runs in seconds, is reproducible by a judge who clones the repo, and decouples the differentiator from the highest-risk task. The Claude agent becomes one hero session recorded for the video rather than a dependency of the metrics.
- Evaluation suite is scheduled BEFORE both UIs, not after. Last-scheduled is first-cut, and this is the one component whose absence changes what the project is: without the metrics table it reverts to a multi-tenant catalog MCP server, which is Razorpay's own listed example for Track 01. Sessions and generator on Day 8, metrics on Day 9, held-out run Day 10 morning, then Next.js.
- Both UIs kept but cut to size: onboarding UI 2hrs (one unstyled page, file input plus four policy fields, no CSV column-mapping preview, no component library) and audit view 1.5hrs (second route, server-rendered read-only AuditEvent table, no filters, no pagination). Down from 6.5hrs to 3.5hrs. If the schedule slips past Day 10 the audit VIEW dies first and a 45-minute CLI printer replaces it.
- Headless spike cut from 4-6hrs to 1.5hrs (signup, test key, one successful POST /v1/orders). Issue #0005 already established every constraint the spike would rediscover, so re-deriving it buys confidence and nothing else. Cheapest 3.5hrs available.
- Merchant prerequisite settled: the target merchant is ALREADY a Razorpay merchant (activated, KYC-complete, taking payments). This project does not onboard anyone to payments; it adds agent-transactability to an existing Razorpay account. Production flow is Partner OAuth authorization with orders created against the merchant's own account via X-Razorpay-Account, so funds land with the merchant and this layer never holds money or becomes a payment aggregator. The shipped build uses logical tenancy under one test account with notes.merchant_id, because Technology Partner status takes 2-3 weeks plus KYC. Pitch consequence: the addressable market is Razorpay's existing merchant base with nothing to migrate, which is a stronger growth story than 'any merchant can sign up' and pre-empts the 'are you becoming an aggregator' objection.
- Project layout: ONE root Bun package plus exactly one workspace member, web/. Not a packages/* monorepo. Critically, web/ NEVER imports the DB layer — next dev and next build run under Node, where 'import { Database } from bun:sqlite' throws. The Next app talks HTTP to the Bun server on localhost:8787 via two internal routes (POST /internal/onboard, GET /internal/audit). This avoids betting Day 10 on Next 16 + Turbopack running under the Bun runtime, and it means one process owns the database, which is the right answer for SQLite anyway. Rejected: two unrelated projects (loses single bun install and one honest commit history) and a packages/core monorepo (real minutes lost to cross-package resolution and build ordering for zero benefit at 39 hours).
- The gate is a PURE FUNCTION with injected data access: src/gate/index.ts exports decide(ctx, req, deps). IDEA.md's architecture diagram already has the eval suite feeding the gate directly, bypassing the MCP layer, and that arrow is load-bearing — if the gate is only reachable through a tool handler then Day 8 must boot an HTTP server per transcript and the 'runs in seconds, reproducible by anyone who clones' property dies. Decided on Day 2 with the contracts rather than on Day 5 while writing the gate.
- Schema decisions where IDEA.md was underspecified: money is integer paise everywhere with a _paise column suffix so unit mistakes are visible at the call site; timestamps are INTEGER Unix epoch MILLISECONDS UTC (Date.now() directly, integer range comparison in the cap query, no TZ bug in a demo recorded in IST); Policy is its own table with merchant_id UNIQUE rather than a JSON blob, so the approval_threshold <= spend_cap check is enforceable as a schema CHECK; Policy.window stored as window_seconds INTEGER, parsed once at onboarding rather than string-parsed on every checkout; Product uses a composite PRIMARY KEY (merchant_id, id) so the agent sees the merchant's real SKU and two merchants shipping SKU-1 is structurally impossible; Order.items is items_json TEXT since nothing queries into it; Order.created_at added because the spend-cap window is defined over it and the cap cannot be implemented without it; Order rows are written on allow and escalate only, never on block; audit_events deliberately has NO foreign keys because it is an append-only ledger that must survive a merchant deletion — an FK cascade would delete evidence.
- Two additions to the DUK-8 contract spec. (1) ALLOWED joins the reason-code union, because the allow branch writes an AuditEvent and reason_code is NOT NULL — without it every eval aggregation writes COALESCE. (2) STALE_CATALOG carries a 'mismatch' discriminator ('price' | 'stock' | 'missing') plus true_price_paise, not just true_stock: the merchant-side-misclaim attack is a PRICE mismatch and the agent's re-plan differs by kind (price means retry at true price, stock means substitute). Without the discriminator the agent infers the kind by comparing numbers, which is fragile, and fragile is what the video would show. Also added UNAUTHENTICATED (DUK-9 asks for a 401 consistent with the envelope) and INVALID_REQUEST as a catch-all so no code path invents a string. Errors are a zod discriminatedUnion on reason_code so the buyer agent gets an exhaustive switch. Deliberately NOT added: prev_event_id — events link by session_id ordered by ts, which idx_audit_session already serves.
- list_products and get_product DO write AuditEvents (rule=ALLOW, decision=allow, reason_code=ALLOWED, amount_paise=NULL). Reason: the stale-price attack class needs the list_products call in the log to PROVE the agent replayed a price it saw at time T. Without those rows the stale-price escape is unprovable from the audit trail and 'reconstructible from the audit log alone' fails for the exact attack the ACP-alignment claim rests on. One line on Day 3, impossible to backfill later.
- REVERSED: Postgres via Docker replaces SQLite. Trigger is the decision to HOST BOTH the dashboard UI and the MCP server live. SQLite on an ephemeral hosting filesystem is untenable, and I had already stated that a live hosted endpoint is the one scenario that flips the recommendation. Postgres also dissolves the Node/Bun split — the Next app can talk to Postgres directly via pg under Node, where bun:sqlite throws — though the two internal HTTP routes remain a valid alternative. Local development uses docker compose. Cost accepted: roughly 1.5-2.5hrs of migration (async plumbing through the gate, repo and eval runner, plus connection pooling and compose config).
- The MCP server and dashboard UI will be DEPLOYED LIVE, but deployment is scheduled Day 11-12 and is explicitly DROPPABLE. Rationale: the architecture must support hosting from Day 1 (hence Postgres now), but the deployment risk belongs at the end where it cannot take down anything load-bearing. If the clock beats it, the submission is still repo plus video and nothing depended on a URL. Upside justifying the 4-6hr total cost: a judge can point Claude Desktop at the live endpoint and shop a real merchant, which is interop rather than a video of interop — the strongest possible proof for a pitch claiming 'any merchant becomes agent-transactable'.
- Hosting platform: Railway for BOTH the Bun MCP server and the Next dashboard. Bun runs natively, managed Postgres sits in the same project with DATABASE_URL injected, one deploy pipeline. Rejected splitting Next onto Vercel: adds CORS plus a second pipeline for no gain.

Blast radius is bounded anyway since the account is Razorpay test mode and cannot move real money, but an unauthenticated public MCP endpoint carrying a Razorpay key is not a posture to ship. The local path must keep working independently — docker compose up -d, bun run db:migrate, bun run eval — because the eval suite's reproducibility claim is load-bearing and must not depend on the server staying up.

Twelve issues of adversarial review history — the globally-false novelty claim, the 51-vs-39-hour schedule math, the gate bug found and fixed — are documentary evidence of exactly what the submission form's 'Build Challenges and Technical Obstacles' field asks for, and almost nobody submits that. So idx_orders_spend_cap is correct.
