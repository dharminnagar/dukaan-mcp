# #0023 FALSE-POSITIVE COST METRIC HAS NO DATA. Supersedes #0021 and #0022, both of which were closed by accident on 2026-08-25 by malformed record_fix calls that omitted issue_id and therefore closed whatever the active issue happened to be. Nothing about the finding was ever resolved. Restating it as the single open actionable item. DUK-19's report on the train split prints 'Blocked benign GMV, UPPER BOUND: 0.00 rupees' because 84 of 84 benign transcripts were ALLOWED. Zero false positives means the figure is trivially zero and measures nothing; recovery rate is NOT MEASURABLE and net NOT COMPUTABLE downstream of the same emptiness, which the report states honestly but which does not make the metric exist. This is the number IDEA.md leans on for its cross-track argument: false-positive cost in rupees of blocked legitimate GMV is meant to be simultaneously the Track 02 honesty metric and the Track 01 growth metric, one number closing both halves. It is currently 0.00 at n equals 0. ROOT CAUSE is src/eval/benign.ts, not the gate: it generates baskets comfortably inside every threshold, so the gate never gets an opportunity to be wrong, and a false-positive rate measured over a population engineered to contain no near-misses is guaranteed zero. FIX: add near-boundary benign sessions — legitimate shopping just under a spend cap, just under an approval threshold, and using the household versus personal-care category ambiguity the DUK-11 seed data already carries for exactly this purpose. SEQUENCING, which matters more than the fix: adding sessions changes the corpus, so the split must be re-frozen afterwards, and that re-freeze has to happen BEFORE DUK-20 scores the held-out split, because that run happens exactly once. Same constraint applies to the pending model-generated adversarial batch from #0010 — do both corpus changes, then re-freeze once, then score.
