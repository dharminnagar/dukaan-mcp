# #0015 VERIFIED DEFECT (DUK-12, found by orchestrator probe not by the implementing agent's own tests): one MCP client making three tool calls produces THREE distinct session_id values in audit_events, not one. Root cause: resolveTenant does `sessionId ?? freshSessionId()`, src/mcp/http.ts reads `mcp-session-id` off the request, but createMcpHandler is running stateless and never issues an Mcp-Session-Id, so the client has nothing to echo back and every request mints a fresh session. Server side is CORRECT and already works: re-running the same probe with an explicit client-supplied `mcp-session-id` header gives 3 audit rows under 1 session_id. Downstream consequences: (1) DUK-20's acceptance criterion 'bun run audit --session=X prints the three linked events of the hero re-plan scenario in order' is unachievable as built, because block/re-plan/success land under three unrelated session ids; (2) idx_audit_session ON audit_events (session_id, ts) is currently dead weight; (3) the sessions table gets one row per tool call, which is semantically wrong; (4) the stale-price proof still works but only via (merchant_id, agent_id) ORDER BY ts, not the session linkage the schema was designed for. NOT a tenancy or spend-cap bug: the cap is correctly scoped to (merchant_id, agent_id, window) per issue #0009, and session_id remains display/audit-grouping only. Two fix options: (a) DUK-17's buyer agent sends a stable mcp-session-id header, one line, works for the hero video since we own that client; (b) enable stateful sessions in createMcpHandler so the SDK issues the id and ANY client including Claude Desktop gets grouping for free, which is what DUK-25's judge-facing demo needs.
