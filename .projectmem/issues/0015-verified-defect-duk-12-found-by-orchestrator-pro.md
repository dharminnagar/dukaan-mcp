# #0015 VERIFIED DEFECT (DUK-12, found by orchestrator probe not by the implementing agent's own tests): one MCP client making three tool calls produces THREE distinct session_id values in audit_events, not one. Root cause: resolveTenant does `sessionId ?? freshSessionId()`, src/mcp/http.ts reads `mcp-session-id` off the request, but createMcpHandler is running stateless and never issues an Mcp-Session-Id, so the client has nothing to echo back and every request mints a fresh session. Server side is CORRECT and already works: re-running the same probe with an explicit client-supplied `mcp-session-id` header gives 3 audit rows under 1 session_id. Downstream consequences: (1) DUK-20's acceptance criterion 'bun run audit --session=X prints the three linked events of the hero re-plan scenario in order' is unachievable as built, because block/re-plan/success land under three unrelated session ids; (2) idx_audit_session ON audit_events (session_id, ts) is currently dead weight; (3) the sessions table gets one row per tool call, which is semantically wrong; (4) the stale-price proof still works but only via (merchant_id, agent_id) ORDER BY ts, not the session linkage the schema was designed for. NOT a tenancy or spend-cap bug: the cap is correctly scoped to (merchant_id, agent_id, window) per issue #0009, and session_id remains display/audit-grouping only. Two fix options: (a) DUK-17's buyer agent sends a stable mcp-session-id header, one line, works for the hero video since we own that client; (b) enable stateful sessions in createMcpHandler so the SDK issues the id and ANY client including Claude Desktop gets grouping for free, which is what DUK-25's judge-facing demo needs.

- 2026-08-25T12:00:57Z `fix`: DUK-28 FIXED, and #0015 with it. resolveTenant now resolves session_id as: honour a supplied mcp-session-id verbatim, else reuse the most recent session for this (merchant_id, agent_id) if it started within SESSION_REUSE_WINDOW_SECONDS (30 minutes), else mint a fresh one via the existing freshSessionId(). The lookup is `SELECT id FROM sessions WHERE merchant_id=$1 AND agent_id=$2 AND started_at >= now() - make_interval(secs => $3::int) ORDER BY started_at DESC LIMIT 1`, which matches idx_sessions_merchant_agent (merchant_id, agent_id, started_at DESC) exactly — the migration already carried that index, so the schema anticipated this. Deliberately a most-recent-within-window lookup and NOT a floor(now/1800) time bucket: a bucket splits any session straddling its boundary, which would break the exact hero beat this ticket exists to fix. Deliberately NOT a stateful transport: createMcpHandler cannot be made stateful per the SDK docs, and the NodeStreamableHTTPServerTransport rewrite would resolve the tenant once at initialize and hold it, so a revoked token would keep working until the session closed, where today every request re-resolves. SAFE because session_id is display and audit-grouping only, never an enforcement key — the rule from issue #0009 — so two merged sessions change the display and nothing about what is allowed. ORCHESTRATOR VERIFICATION, the original failing case end to end with a real MCP client sending NO header across three separate connections: 3 audit rows, 1 distinct session_id, and 1 sessions row where it was previously 1 per call. Also held when the three calls were fired concurrently, though honestly: the read-then-write window does exist in principle and a rare split is possible. Unlike the spend cap that consequence is cosmetic rather than a bypassed rule, so it does not warrant a lock. Full suite 153 pass / 0 fail across 13 files twice, typecheck exit 0, eslint clean. Cost: one extra DB query per resolve, and only when the caller supplies no header. LIMITATION for the README: audit sessions are derived per agent per time window, not negotiated at the protocol level, so two genuinely separate shopping sessions inside one window merge into one audit group.
