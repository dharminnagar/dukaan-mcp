# #0024 FRAMING GAP the README must close, and it is the first question a payments panel will ask: spend_cap is a MERCHANT-IMPOSED underwriting limit, not a buyer-funded budget, and nothing in this system funds an agent at all. Surfaced by Dharmin on 2026-08-25 after the claude.ai demo: 'how can a user allocate funds to the agent, it just started transacting and the order didn't even need that to fulfill'. The precise answer is that nothing was fulfilled and nothing was paid — status 'created' means a Razorpay Order object exists as an intent to collect, with no payment, no authorization and no money moved. But the underlying question exposes a real asymmetry in the pitch. The gate answers 'should THIS MERCHANT let this agent spend this much here', which is merchant-side underwriting and is genuinely the thing Razorpay would need. It does NOT answer 'whose money is this and who authorised the spend', because there is no buyer-side funding primitive anywhere in the build: no wallet, no mandate, no pre-authorised reserve. A reader who assumes spend_cap is the buyer's budget will conclude the system lets an agent spend money nobody allocated. The real-world answer to buyer-side funding is exactly UPI Reserve Pay, AP2's signed mandates and NPCI's UAP — a buyer pre-authorises a reserved amount with a cap and a validity window that an agent draws against — and IDEA.md already records Reserve Pay as unbuildable today (no public API reference, no test-mode sandbox, closed pilot). So the honest framing is already available and just needs stating: authorisation is a bounded human step because regulation currently requires one, the cap is the MERCHANT's exposure limit rather than the buyer's balance, and the gate is the layer already sitting there for when Reserve Pay opens. ACTION for DUK-21: add an explicit paragraph distinguishing merchant-imposed cap from buyer-funded budget, and name the missing primitive rather than letting a reader assume it exists.
