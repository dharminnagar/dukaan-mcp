# #0018 SPEND CAP TOCTOU RACE, found by orchestrator probe against the DUK-13 checkout flow. Three checkouts fired CONCURRENTLY by the same agent, each 40000 paise against a 100000 cap: all three returned allow and 120000 paise persisted, breaching the cap by 20000. Cause: decide() reads spentInWindowPaise and the checkout handler writes the orders row in two separate statements with no transaction, lock, or serialisation between them, so concurrent checkouts all observe the same pre-write total. Reproduced deterministically with Promise.all over three calls. WHY THIS IS SIGNIFICANT RATHER THAN A GENERIC CONCURRENCY NIT: it is adversarial class #1, budget-split evasion, in its most direct form — parallel instead of sequential. The eval suite replays transcripts sequentially, so it will report budget-split as CAUGHT while the parallel variant escapes undetected. A metrics table claiming the cap holds, published next to a gate that a client can beat by issuing three simultaneous tool calls, is exactly the kind of gap the escapes list exists to surface. MCP clients can and do parallelise tool calls, so this is inside the declared threat model, not outside it. NOT a flaw in DUK-13's implementation, which follows the specified flow correctly; it is a gap in the gate's contract. PROPOSED FIX, cheap and non-invasive: take a Postgres transaction-scoped advisory lock keyed on (merchant_id, agent_id) in the CHECKOUT HANDLER around decide() plus insertOrder. That leaves decide() a pure function with injected deps, so src/eval/ is unaffected and the offline reproducibility property survives. Alternative if not fixed: state it plainly in the README limitations list next to the unauthenticated-agent-identity item, because a judge probing the gate will find it.

- 2026-08-25T06:39:59Z `fix`: DUK-29 spend-cap parallel race FIXED in commit 480c367. withAdvisoryLock(key, fn) added to src/db/pool.ts (one new export; pool, query, queryOne, withTransaction and closePool verified untouched): opens a short transaction on its own pooled client, takes SELECT pg_advisory_xact_lock(hashtext($1)), runs fn, commits. Transaction-scoped rather than session-scoped deliberately — Postgres releases it however the transaction ends, so nothing must remember to unlock if the process dies mid-checkout. The checkout handler in src/mcp/http.ts wraps decide(), the Razorpay call and insertOrder in one lock keyed `${merchant_id}:${agent_id}`. THE RAZORPAY CALL STAYS INSIDE THE LOCK: the lock must already be held when decide() runs because the branch is unknown until it returns, so releasing between decide() and insertOrder to spare the network round trip would merely shrink the race window rather than close it. Cost is that one agent serialises behind its own payment latency; other agents and merchants never contend since keys are independent. Escalate does not need the lock for correctness (SPEND_CAP_SQL filters status IN ('created','authorized'), so escalated orders never count) but ends up inside it structurally. VERIFICATION, orchestrator-independent and with different parameters from the agent's own test: 6 concurrent checkouts through the real MCP tool, cap 90000, item 50000 — exactly 1 allowed, 50000 persisted, cap held. Full suite 137 pass / 0 fail across 12 files twice, typecheck exit 0. IMPORTANT BOUNDARY, now documented in code: the fix protects the CHECKOUT TOOL path, not decide() itself. A probe of 3 concurrent decide()+insertOrder calls bypassing the handler still persisted 150000 against a 100000 cap. That is by design — the lock lives in the handler so decide() stays pure and src/eval runs with no lock, transaction or server — but it means ANY caller acting on an allow must serialise itself. src/eval/runner.ts satisfies this by replaying strictly sequentially, and both src/gate/index.ts and that loop now carry comments saying that parallelising the runner for speed would break the cap silently and corrupt the metrics rather than failing loudly.
