# #0018 SPEND CAP TOCTOU RACE, found by orchestrator probe against the DUK-13 checkout flow. Three checkouts fired CONCURRENTLY by the same agent, each 40000 paise against a 100000 cap: all three returned allow and 120000 paise persisted, breaching the cap by 20000. Cause: decide() reads spentInWindowPaise and the checkout handler writes the orders row in two separate statements with no transaction, lock, or serialisation between them, so concurrent checkouts all observe the same pre-write total. Reproduced deterministically with Promise.all over three calls. WHY THIS IS SIGNIFICANT RATHER THAN A GENERIC CONCURRENCY NIT: it is adversarial class #1, budget-split evasion, in its most direct form — parallel instead of sequential. The eval suite replays transcripts sequentially, so it will report budget-split as CAUGHT while the parallel variant escapes undetected. A metrics table claiming the cap holds, published next to a gate that a client can beat by issuing three simultaneous tool calls, is exactly the kind of gap the escapes list exists to surface. MCP clients can and do parallelise tool calls, so this is inside the declared threat model, not outside it. NOT a flaw in DUK-13's implementation, which follows the specified flow correctly; it is a gap in the gate's contract. PROPOSED FIX, cheap and non-invasive: take a Postgres transaction-scoped advisory lock keyed on (merchant_id, agent_id) in the CHECKOUT HANDLER around decide() plus insertOrder. That leaves decide() a pure function with injected deps, so src/eval/ is unaffected and the offline reproducibility property survives. Alternative if not fixed: state it plainly in the README limitations list next to the unauthenticated-agent-identity item, because a judge probing the gate will find it.
