# #0005 BLOCKER: a headless agent cannot AUTHORIZE a payment on a vanilla Razorpay test account. Every documented server-to-server route is gated. S2S Redirect and S2S JSON v1/v2 all carry a 'raise a request with our Support team to get this feature enabled' block, and S2S generally requires PCI-DSS certification. UPI Collect (the server-side VPA flow, success@razorpay) was DEPRECATED 28 Feb 2026 per NPCI — new users must use UPI Intent. UPI Payment Links are explicitly not supported in test mode. Smart Collect test payments are Dashboard-button-only. Standard Checkout in test mode requires clicking a mock bank page and entering an OTP in a browser. Capture is NOT the problem (auto-capture is the account default and applies to Orders-API payments); AUTHORIZATION is. Only documented headless simulate-payment endpoint is POST /v1/bharatqr/pay/test, and BharatQR itself needs a support ticket to activate.

- 2026-08-25T11:32:06Z `fix`: RESOLVED by the human-approved handoff decision, which turned the blocker into a framing advantage. The build does not attempt headless authorization: the agent shops, the gate decides, a real Order is created through POST /v1/orders, and authorization is a bounded human approval step, cited to Indian payments regulation and to the fact that UPI Reserve Pay and NPCI's UAP exist precisely because an agent cannot autonomously authorize a UPI payment today. That is the only currently legal shape, and stating it with the citation is a stronger signal than faking an autonomy the law forbids. Playwright driving the hosted checkout was rejected explicitly: 6 to 10 hours to fake something regulation does not permit. The S2S JSON v2 and BharatQR support requests remain a free upgrade if granted and nothing in the plan waits on them — that is DUK-7, and a setup guide now exists for raising them.
