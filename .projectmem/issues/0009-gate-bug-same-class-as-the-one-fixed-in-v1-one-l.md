# #0009 GATE BUG, same class as the one fixed in v1, one level up. IDEA.md enforces the spend cap over session_id. An agent defeats that by opening a new SESSION, exactly as a global cap is defeated by opening a new conversation. Adversarial class #1 (budget-split evasion) is therefore trivially winnable against the defense as written, and it is the first thing a judge will ask about. Fix (~30 min, one WHERE clause): enforce over (merchant_id, agent_id, window); session_id becomes display and audit-linkage grouping only. Policy.window and Session.agent_id already exist in the data model and are currently unused. Residual to state openly: agent_id is self-asserted unless bound to the auth token — either issue per-agent credentials or write in the README that agent identity is unauthenticated in this build, which is precisely the gap NPCI's UAP exists to fill.

The spend cap is enforced over (merchant_id, agent_id, window) and never session_id: SPEND_CAP_SQL filters on merchant_id, agent_id and a created_at window with status IN ('created','authorized'), and session_id never enters the enforcement query. Second, mutating SPEND_CAP_SQL back to session_id scope — the exact bug this issue described — turns the suite 5 red, and mutating it to merchant_id-only scope turns it 13 red, so the tests demonstrably can fail. Third, multi-agent isolation is tested from both sides: agent B is allowed while agent A is blocked on the identical order shape, which a silently-disabled cap could not pass. The residual this issue flagged is also addressed: agent_id is derived from the bearer token so an agent cannot rename itself, and the limitations list states plainly that agent identity is otherwise unauthenticated, which is the gap NPCI's UAP exists to fill.
